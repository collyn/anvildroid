# Installed keymap editor: KDE host check, 2026-10-20

This run responds to the user's report that the newly installed keymap editor
was difficult to use and appeared unreliable. It exercises the installed
application on the current KDE KWin Wayland 6.6.6 desktop, Android 13 GAPPS and
the managed `test` runtime. Input enters the real desktop through a temporary
uinput device; Spectacle captures the actual app windows. This is separate from
the earlier private Xvfb/Weston acceptance fixtures.

## Reproduced problems and changes

- Add/place followed by typing Q left an unassigned `KEY` marker: capture had
  required a separate Key button click. Placement now immediately waits for a
  keyboard binding. Dragging an existing control keeps its binding.
- Selecting a type required cycling through nine types. The existing type
  button now opens a nine-item picker, including WASD, Swipe, Mouse touch and
  Look. Outside click or Escape dismisses the picker without applying another
  toolbar action.
- Switching a mouse-bound control's gesture reset its source to keyboard.
  Gesture changes now retain a mouse trigger; selecting the current type also
  preserves its parameters. Markers show M1/M2, WASD and MOUSE.
- A type conversion inheriting a conflicting WASD trigger now waits for a
  replacement key. On the actual editor, converting the existing Look control
  through WASD back to Look accepted T, with no extra Key click. Cancel then
  preserved the saved profile bytes.
- The controller reported `Incomplete keymap inventory frame` for a valid
  saved empty launcher profile. The subprocess runner stripped the final
  profile newline and frame delimiter. Inventory now requests unchanged
  whitespace; the production API lists the profile with `invalid_count=0`.

## Actual input results

Calculator was used to verify visible key assignment and a mapped press on
the authored digit. A temporary Touch Probe was then authored through the
installed editor; profiles were not generated by a fixture. The mouse binding
was changed Basic → Swipe → Basic and retained source=mouse in the saved file.
The final installed bridge was restarted and the saved profile reloaded before
repeating the six main playback scenarios.

| Scenario | Observed result |
| --- | --- |
| Keyboard tap | Finger DOWN/UP at the authored point |
| Fixed mouse-button tap | Right button produced finger DOWN/UP at its authored point |
| Swipe + Hold | MOVE reached the endpoint; contact remained down after 550 ms and lifted on key release |
| WASD diagonal | One joystick contact moved with combined directions and lifted after release |
| Hold Look | Pointer movement produced finger MOVE inside the authored region |
| WASD + Look + mouse button | Three simultaneous fingers, balanced releases |
| Mouse touch | Left press/drag/release produced finger DOWN/MOVE/UP |

Each recorded gesture passed the existing MotionEvent sequence validator:
`SOURCE_TOUCHSCREEN=0x1002`, `TOOL_TYPE_FINGER`, no stale-contact warning and final
`activeAfter=0`. Save, restart/reload, direct type selection, immediate binding,
conflict replacement, visible M2/WASD labels and byte-preserving Cancel were
also checked on the actual desktop. Raw local evidence is under
`target/keymap-fix-tests/host/` and `target/keymap-*.png`.

The old target-SDK-28 diagnostic APK was rejected by Play Protect. A separate
target-SDK-33 copy was used for these touch checks; verification settings were
left enabled. The diagnostic APK and both test-created profiles were removed.
The original empty launcher profile was preserved, the runtime was left running
with its full Android UI restored, and the temporary input helper was stopped.
RustDesk's existing service/server/tray/connection processes remained running.
